CommonQt6

CommonQt6 is a Common Lisp binding to the smoke library for Qt6.

Download

Get it from git: 

git clone https://github.com/commonqt/commonqt6.git
Github page: https://github.com/commonqt/commonqt6.

Support


Reporting bugs: https://github.com/commonqt/commonqt6/issues.

Dependencies (C++)

CommonQt6 needs:

  • Qt 6 libraries (target: Qt 6.11).
  • CMake 3.22+ and a C++17 compiler.
  • The smoke library for Qt6.
    Build from git: smokegen (branch: clang-qt6) first, and then smokeqt (branch: qt6).
    smokegen also requires LLVM/Clang libraries (tested with LLVM 19.x).
  • The commonqt6 C++ library must be compiled separately using CMake before loading the Lisp system. See the README for detailed build instructions.

All built libraries (Qt6, smokegen, smokeqt, commonqt6) must be accessible through PATH.

Windows

  • Visual Studio 2022 Community Edition with the C++ Desktop Development Kit.
  • Additional build tools: Python 3.8+, Node.js 20+, Ninja, Bison 3.7+, Flex 3.6.4+, GPerf, xmlstarlet.
  • All projects (Qt, LLVM, smokegen, smokeqt, commonqt6) must be compiled in RELEASE configuration.

Dependencies (Lisp)

CommonQt6 is mostly tested with SBCL and Clozure CL. It has been reported to run on Allegro and LispWorks in the past, and can also run on ABCL and ECL, albeit slower than desired.

Lisp dependencies (automatically pulled in via Quicklisp/ASDF): CFFI, named-readtables, cl-ppcre, Alexandria, closer-mop, iterate, trivial-garbage.

Installation

Before loading the Lisp system, the C++ library commonqt6 must be compiled separately using CMake. See the README on the Github page for full build instructions.

Quicklisp is the preferred way to install the Lisp side: 

(ql:quickload :qt)

The ASDF system is named :qt. There is also :qt+libs which additionally loads the qt-libs system for locating precompiled libraries.

Examples

  • Currency conversion dialog — A simple GUI example demonstrating Qt signal/slot connections and widget layout.
  • Another tutorial example is available in the tutorial directory of the repository.

QApplication

The constructor for QApplication requires more FFI magic than you would probably want to write yourself, because it is designed to take the (int* argc, void** argc) arguments from a main function in C.

Use the make-qapplication function provided by Qt instead, which takes string arguments and converts them. QApplication can be instantiated only once, therefore make-qapplication sets *qapplication* variable to the produced instance, and only creates a new one if *qapplication* is NIL. It also automatically loads the qt6core and qt6gui smoke modules.

Examples: 

(make-qapplication)
(make-qapplication "-display" ":0")

Creating a main window

The with-main-window macro can be used as an entry point of a program: 

(with-main-window (window (#_new QWidget)))

is equivalent to doing: 

(make-qapplication)
(with-objects ((window (#_new QWidget)))
  (#_show window)
  (#_exec *qapplication*))

The body of with-main-window is executed between the creation of the window and showing it, allowing additional setup: 

(with-main-window (window (#_new QWidget))
  (#_setWindowTitle window "My App"))

After closing the window, it can be executed again.

Loading Modules

Loading additional modules is done using ensure-smoke. make-qapplication already loads qt6core and qt6gui; anything else has to be loaded explicitly, e.g., (ensure-smoke :qt6svg).

Module names are normalized automatically: a name like :qtsvg is converted to qt6svg internally, so both forms work.

Calling instance methods

Use the #_ reader macro to invoke Qt methods easily.

Example: 

(#_setGeometry window 100 100 500 355)
(#_show window)

The first argument is the instance to call the method on, the following arguments are passed on to the method.

Method names are case sensitive.

To enable the reader macro, use (named-readtables:in-readtable :qt) at the top of your file.

Calling static methods

Static methods:

Example: 

(#_Qt::blue)

Instantiating Qt classes

The reader macro for #_ has a special case: If it is followed by new, it keeps reading to find a class name, then returns a call to a constructor instead.

Example: 

(#_new QPushButton "Quit")

Class names are case-sensitive.

In this case, the macro expands into a use of the qt:new function.

Connecting signals and slots

The function CONNECT is used to connect signals and slots in different ways:

  • (connect sender "signal()" receiver "slot()")
  • (connect sender "signal(int)" (lambda (int) (print int)))
  • (connect sender "signal(int)" receiver (lambda (receiver int) (print int)))
  • (connect sender "signal()" receiver (qsignal "signal()"))
with-signals-blocked macro is used to block the signals emitted by objects to improve performance or avoid endless recursion: 
(with-signals-blocked (button linedit)
  ...)

Subclassing C++ classes

You can make "subclasses" using smoke like this: 

(defclass button ()
    ()
  (:metaclass qt-class)
  (:qt-superclass "QPushButton"))

(defmethod initialize-instance :after ((instance button) &key)

  ;; Must call the C++ constructor here first:
  (new instance "label")

  ;; can call C++ methods on this lisp object afterwards:
  (connect instance "clicked()" *qapplication* "quit()")

Always specify the metaclass. Specify the qt-superclass only when not subclassing another such Lisp class that already has it. Above we didn't specify a superclass, so it was defaulted to qt:dynamic-object, a subclass of qt:qobject.

Always call the C++ constructor from initialize-instance. Note the use of qt:new with an existing instance that already knows its class (but doesn't have a pointer slot yet).

Overriding C++ methods

In a subclass (see the example above), you can override C++ methods like this: 

(defclass canvas ()
    ()
  (:metaclass qt-class)
  (:qt-superclass "QWidget")
  (:override ("paintEvent" paint-event)))

(defmethod paint-event ((this canvas) paint-event)
  (declare (ignore paint-event))
  (let ((painter (#_new QPainter this)))
    ... paint something ...
    (#_end painter)))

To call the C++ method in an overridden method, either call-next-qmethod can be used, when the return value is needed, or stop-overriding can be used, which performs a non local transfer of control and never returns, but is implemented more efficiently.

Note that we always intercept all methods of the specified name, ignoring their argument type signature. In this case, there's only one method called paintEvent, so that is safe to do. If there was a second paintEvent method without arguments, you'd have to use &optional or &rest to avoid errors.

Defining signals and slots

In a subclass (see the example above), you can add signals and slots. Here is a real example from tutorial 13: 

(defclass cannon-field ()
    (...)
  (:metaclass qt-class)
  (:qt-superclass "QWidget")
  (:slots ("setAngle(int)" (lambda (this newval)
                             (setf (current-angle this)
                                   (min (max 5 newval) 70))))
          ("setForce(int)" (lambda (this newval)
                             (setf (current-force this)
                                   (max 0 newval))))
          ("void moveShot()" move-shot)
          ("void shoot()" shoot)
          ("void setGameOver()" set-game-over)
          ("void restartGame()" restart-game))
  (:signals ("angleChanged(int)")
            ("forceChanged(int)")
            ("void hit()")
            ("void missed()")
            ("void canShoot(bool)")))

Note the use of lambda to pre-process values and swap arguments in slots that are meant to just call a CLOS accessor eventually, and the use of lisp function names elsewhere.

Signals don't have a corresponding Lisp function. Emit them like this: (emit-signal object signal-name arguments)

Object lifetime

Qt objects are heap-allocated and must be explicitly deleted when no longer needed. CommonQt6 provides with-objects as the standard idiom for automatic cleanup: 

(with-objects ((button (#_new QPushButton "Click me"))
               (label  (#_new QLabel "Hello")))
  ;; button and label are deleted when this form exits,
  ;; even if an error is signalled
  (#_show button)
  (#_show label))

To delete an object immediately, use (#_delete object). After deletion, the pointer is marked as :deleted and any further method calls on it will signal an error.

Qt parent/child relationships also manage lifetime: when a parent is deleted, Qt automatically deletes all its children. CommonQt6 tracks this via a C++ deletion callback, so Lisp-side qobject instances are updated correctly when Qt deletes them.

note-deleted can be called manually to inform Lisp that an object has been deleted outside of CommonQt6's awareness.

Disconnecting signals

The disconnect function mirrors connect and accepts the same argument forms:

  • (disconnect sender "signal()" receiver "slot()")
  • (disconnect sender "signal(int)" function)
  • (disconnect sender "signal(int)" receiver function)

For dynamic (Lisp lambda) connections, the exact same function object that was passed to connect must be passed to disconnect.

Enum operations

Qt methods frequently return and accept enum values. CommonQt6 wraps them as enum objects carrying both the numeric value and the type name. Several utilities are provided:

  • (enum-value e) — extract the integer value from an enum.
  • (enum= a b) — true if two enums have the same type and value.
  • (enum-equal a b) — true if two enums (or an enum and an integer) have the same value, ignoring type.
  • (enum-or e1 e2 ...) — bitwise OR of enum or integer values (for flag combinations).
  • (enum-andc e1 e2 ...) — bitwise AND-complement (for clearing flags).

Example — combining window flags: 

(#_setWindowFlags window
  (enum-or (#_Qt::Window) (#_Qt::FramelessWindowHint)))

Type checking

qtypep tests whether a Qt object is an instance of a given Qt class (by name or class object), respecting the C++ inheritance hierarchy: 

(qtypep button "QPushButton")  ; => T
(qtypep button "QWidget")      ; => T  (QPushButton inherits QWidget)

qsubclassp tests whether one Qt class is a subclass of another: 

(qsubclassp (find-qclass "QPushButton") (find-qclass "QWidget"))  ; => T

null-qobject-p tests whether an object is a null Qt pointer: 

(null-qobject-p (#_QCoreApplication::instance))  ; => T if no app exists

cast reinterprets an object as a different Qt class: 

(cast "QWidget" button)  ; returns button viewed as a QWidget

REPL integration

The :qt-repl system (load with (ql:quickload :qt-repl)) allows running the Qt event loop on a dedicated background thread so that the REPL remains fully interactive.

Start the GUI thread once at the beginning of a session: 

(qt-repl:start-gui-thread)

After this, any Qt GUI code can be evaluated interactively: 

(qt-repl:eval-in-gui-thread
  (with-objects ((w (#_new QWidget)))
    (#_setWindowTitle w "Hello from REPL")
    (#_show w)))

If Swank/SLIME is loaded, start-gui-thread automatically installs a REPL hook so that all subsequent REPL input is routed through the GUI thread transparently — no need to wrap calls in eval-in-gui-thread explicitly.

Note: on macOS, the GUI thread must be the initial OS thread. On SBCL/macOS this is handled automatically.

Qt properties

Qt object properties (as defined by Q_PROPERTY) can be read at runtime using the property function: 

(property button "text")    ; => "Click me"
(property button "enabled") ; => T

To set a property, use the #_setProperty method: 

(#_setProperty button "text" "New label")

The second return value of property indicates whether the property exists on the object (T) or not (NIL). See also the QDESCRIBE for objects section, which lists all properties and their current values at the REPL.

Known issues

Build configuration

On Windows, Qt6, LLVM, smokegen, smokeqt, and commonqt6 must all be compiled in RELEASE configuration. Qt6 differentiates debug vs. release DLLs by a suffix (e.g., Qt6Core.dll vs. Qt6Cored.dll), and the smoke libraries cannot cope with this difference.

Slime on Windows

Running from Slime under Windows doesn't appear to work. Specifically, if the implementation is started as a subprocess of Emacs. To work around the following has to be executed first: 

(with-main-window (window (#_new QWidget)) (#_show window) (#_hide window))
All subsequent windows do not need this and everything else should work normally.

Another work around, the implementation has to be started from cmd.exe, the swank server created and then Emacs can connect to it. An easy way to achieve that is to find the file start-swank.lisp in the slime directory and do

sbcl --load start-swank.lisp

And then do M-x slime-connect. start-swank.lisp can be edited to change the port and other settings.
